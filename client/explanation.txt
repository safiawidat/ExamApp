ExamApp - Project Explanation

1. Project purpose

ExamApp is a full-stack examination application for lecturers and students. The current implementation includes Milestones 1-3: authentication, lecturer-owned authoring, publication, question notices, student-safe exam delivery, and one final submission per student per exam.

Submitted answers are stored but are not graded. The project does not yet provide grading, scores, feedback, or results.

2. Full-stack architecture

React client -> Express API -> PostgreSQL

The React client sends JSON requests to the Express API. The server validates requests, authenticates JWT bearer tokens, enforces role and ownership rules, and uses repositories to read and write PostgreSQL. PostgreSQL is the source of truth.

The microservices directory is a preserved homework demonstration and is not the main ExamApp runtime.

3. User roles

Lecturer:
- Uses a controlled account created by the server seed command.
- Can list shared exam types and manage exam types the lecturer owns.
- Can create and manage owned draft exams and their questions.
- Can publish a non-empty draft.
- Can open notice management for an owned published exam, view questions in stored order, see an existing notice or No notice, and add, edit, or delete a separate above/below notice.

Student:
- Can register publicly and log in.
- Can view only published exams.
- Can open student-safe exam detail.
- Can submit one final set of answers for each exam.
- Cannot access lecturer endpoints or private answer data.

4. Main implemented features

- Public student registration and controlled lecturer seeding
- Login, logout, JWT authentication, and session restoration
- Shared exam-type catalog with creator-scoped mutations
- Lecturer-owned draft exam authoring
- Multiple-choice, true/false, and short-answer questions
- Question editing, type changes, ordering, deletion, and position compaction
- Final publication for non-empty exams
- Separate above/below question notices for published exams
- Published student catalog and student-safe exam detail
- Transactional final submission with explicit unanswered rows
- Submitted-state isolation for each authenticated student

5. Lecturer workflow

The lecturer signs in and enters the existing TeacherDashboard component. The dashboard loads the shared exam types and the lecturer's own exams from the API. Draft exams expose authoring: the lecturer can choose an owned or shared exam type, add all three question types, edit or delete questions, and reorder them. A non-empty draft can be published after confirmation. Published exam and question content cannot be edited, deleted, or reordered, and no unpublish operation exists. Only published exams expose Manage notices. That workspace shows questions in stored order, displays an existing notice or No notice, supports add, above/below placement, edit, and delete, and returns to the exam dashboard.

6. Student workflow

The student registers or logs in and enters StudentPortal. The portal loads the published catalog first and requests full exam detail only when the student opens an available exam. StudentForm renders ordered questions and optional notices, collects answers, and asks for final confirmation. After a successful submission, the catalog marks that exam as submitted and disables it for that student.

7. Main client components

- App: restores sessions and selects the lecturer or student flow.
- NavigationMenu: shows the current identity and handles logout.
- Login and Register: collect authentication input and display safe request errors.
- TeacherDashboard: coordinates exam types, draft authoring, publication, and the published-exam notice workspace.
- ExamTypeManager: manages owned exam types and labels shared types.
- ExamManager: manages draft exams and publication.
- QuestionEditor and QuestionForm: manage all three question types and order.
- QuestionNoticeEditor: shows stored-order published questions and manages separate above/below notices without exposing question editing.
- StudentPortal: loads the student catalog, detail, and submission states.
- StudentForm: renders safe questions and notices and creates the final answer payload.

8. Client API modules

- apiClient.js provides JSON requests, API base configuration, bearer tokens, and normalized API errors.
- authService.js manages login, registration, session restoration, and logout.
- examTypeService.js handles the lecturer exam-type API.
- lecturerExamService.js handles lecturer exams and publication.
- questionService.js handles question creation, updates, deletion, and ordering.
- questionNoticeService.js performs authenticated notice reads, saves, and deletions and validates notice responses.
- studentExamService.js handles the student catalog, detail, and final submission.
- studentExamValidation.js rejects malformed or private student data and validates answers.

Only the JWT is stored in sessionStorage. The client does not store user accounts or exam records as its source of truth.

9. Main server layers

Routes define the public HTTP contract and apply authentication and role middleware. Controllers translate HTTP requests and responses. Services validate payloads and enforce workflow rules. Repositories use parameterized PostgreSQL queries and transactions. The central error handler returns safe client messages.

10. Database entities

The database stores:
- users and roles
- exam types
- exams
- questions
- multiple-choice options
- question notices
- exam submissions
- submission answers
- applied migration versions

Migrations 001-004 create and protect the authoring, question-type, submission, and notice structures. Applied versions are recorded in schema_migrations and successful reruns are skipped.

11. Authentication and authorization

Public registration always creates a student and rejects a supplied role. Lecturer accounts are created through controlled environment-driven seeding. Passwords are hashed with bcrypt. Successful login and registration return a signed JWT. Protected requests reload the user from PostgreSQL before authorization. Missing authentication returns 401, the wrong role returns 403, and owner-scoped lecturer resources use hidden 404 behavior where applicable.

12. Publishing and immutability

A draft exam can be edited, reordered, or deleted. It must contain at least one question before publication. Publishing is final in the current implementation, and there is no unpublish endpoint. Published metadata, questions, options, answer keys or reference answers, order, and deletion are locked by the authoring services. Notices remain separately manageable for owned published exams and do not change that immutability.

13. Question notices

A question notice is stored separately from question content. One notice may exist for each question on an owned published exam. Its trimmed message is limited to 1000 characters, and its placement is above or below the specific question. Notice creation, replacement, reading, and deletion do not edit the immutable published question. StudentForm renders the notice at its requested placement.

QuestionNoticeEditor uses questionNoticeService.js to load and manage notices. It orders questions by stored position, shows each existing notice or No notice state, and supports adding, changing above/below placement, editing, and deleting notices. It returns to the exam dashboard and locks notice controls and back navigation while a mutation is pending. Only published exams expose this workspace, and it has no question-content editing controls.

14. Student-safe delivery

Only published exams appear in the student catalog. Server ordering is preserved. Exam detail contains prompts, points, positions, safe option identifiers and text, and optional notices. It excludes option correctness, correct answers, reference answers, lecturer identity, scores, and feedback. Submitted state is calculated only for the authenticated student.

15. Final submission behavior

The public request contains an answers array. Every exam question must appear exactly once. A multiple-choice response uses selected_option_id, a true/false response uses boolean_answer, and a short response uses text_answer. Boolean false is a valid answer. An object containing only question_id represents an unanswered question and produces an answer row with null value columns.

Duplicate, missing, and unknown question IDs are rejected. An option must belong to its question, and answer fields must match the question type. The submission and all answer rows are inserted in one transaction. The database allows only one submission for each exam/student pair, so a duplicate final submission returns 409. The confirmation contains no grade, score, feedback, result, or correctness data.

16. Testing and validation

Approved final validation:
- Client: 19 test files, 289/289 tests passed across repeated ordinary npm.cmd run test:run runs.
- Vitest maxWorkers: 2 is a deterministic test-runner worker cap for the ordinary command.
- Explicit serial validation with npm.cmd run test:run -- --maxWorkers=1 also passed.
- Client lint passed with zero warnings or errors.
- Client production build passed with 38 modules transformed.
- Server: 8 test files, 166/166 PostgreSQL integration tests passed.
- HTTP smoke: 99/99 checks passed.
- Migrations 001-004 passed on a fresh disposable PostgreSQL database, and the rerun reported that the schema was already up to date.

Server integration tests require TEST_DATABASE_URL and TEST_DATABASE_ISOLATED set exactly to true. The test URL never falls back to DATABASE_URL and must never point to development, shared, staging, or production data.

17. Security decisions

- Password hashes, secrets, and private user fields are never returned.
- Public registration cannot choose a role.
- Lecturer exam access is owner-scoped, and exam-type mutations are creator-scoped.
- SQL values are parameterized.
- Multi-record question and submission changes use transactions.
- Published content is protected from authoring mutations.
- Student projections and client validation reject correctness and result fields.
- The JWT is the only authentication value stored in sessionStorage.

18. Current limitations

- No unpublish workflow is implemented.
- No automated or manual grading is implemented.
- No score, feedback, or results view exists.
- Final answers cannot be revised after submission.
- Final deployment is not yet documented or complete.
- The preserved microservices homework remains separate from the main runtime.

19. Git workflow

Development uses feature branches, review or pull requests, and integration through dev before a later release to main. The documentation describes the current Milestones 1-3 implementation without claiming that a particular feature branch is already merged.
